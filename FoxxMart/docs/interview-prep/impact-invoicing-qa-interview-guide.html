PostgreSQL auditing

Use SQL to find disagreement

Examples follow your Django invoice model. Confirm live table names with \dt or information_schema.tables, and run auditing through a read-only role/transaction.
Invoice snapshot total vs item totals
WITH invoice_lines AS (
  SELECT i.id, i.public_id, i.total AS invoice_total,
         SUM((line->>'line_total')::numeric(12,2)) AS calculated_total
  FROM account_invoice i
  CROSS JOIN LATERAL jsonb_array_elements(i.items) line
  GROUP BY i.id, i.public_id, i.total
)
SELECT public_id, invoice_total, calculated_total,
       ROUND(invoice_total - calculated_total, 2) AS discrepancy
FROM invoice_lines
WHERE ROUND(invoice_total - calculated_total, 2) <> 0;

The CTE expands JSON lines, aggregates per invoice and returns only mismatches. Expected pass condition: zero rows.

Confirmed Axis orders with missing/mismatched invoices
SELECT o.id, o.transaction_id,
       ROUND(SUM(oi.quantity * p.price), 2) AS line_total,
       i.total AS invoice_total
FROM "Axis_order" o
JOIN "Axis_orderitem" oi ON oi.order_id=o.id
JOIN "Axis_product" p ON p.id=oi.product_id
LEFT JOIN account_invoice i
  ON i.store_slug='axis' AND i.order_reference=o.id::text
WHERE o.status='Payment Confirmed, Processing Order'
GROUP BY o.id,o.transaction_id,i.total
HAVING ROUND(SUM(oi.quantity*p.price)-COALESCE(i.total,0),2) <> 0;

Explain the LEFT JOIN: it deliberately keeps confirmed orders with no invoice.

Rounding, tax and delayed job patterns
-- Define first: is tax rounded per line or at invoice total?
SELECT line_id, ROUND(net_amount * tax_rate, 2) AS expected_tax, recorded_tax
FROM invoice_line_audit_view
WHERE ABS(recorded_tax - ROUND(net_amount*tax_rate,2)) > 0.01;

-- Confirmed orders older than agreed grace period with no invoice
SELECT o.id,o.transaction_id,o.date_ordered
FROM "Axis_order" o LEFT JOIN account_invoice i
ON i.store_slug='axis' AND i.order_reference=o.id::text
WHERE o.status='Payment Confirmed, Processing Order'
AND o.date_ordered < NOW()-INTERVAL '10 minutes' AND i.id IS NULL;

SQL interview prompts

  • Why numeric, not float, for money? Exact decimal arithmetic.
  • Why CTEs? Named logical steps/readability; not automatically faster.
  • How avoid false positives? Define precision, timezone, eventual-consistency window and allowed status exceptions.
  • How audit at scale? Scheduled query, metric, alert threshold, owner, runbook and sampled verification.

  • I can explain per-line vs per-invoice rounding.
REST APIs & webhooks

Test promises at every boundary

Contract checklist

  • Required fields, types, formats, enums, nullability.
  • Status codes, error shape, headers, pagination and versions.
  • Authentication: anonymous, wrong user, wrong store, staff.
  • Idempotency: repeat request must not create a second invoice.
  • Money: currency and decimal-safe fields, not unqualified floats.
  • Backward compatibility: consumers tolerate additive fields.

High-value negative cases

  • Empty cart, stale price, stock failure, malformed quantity.
  • Invoice ID from another user/store.
  • Replay, reorder and duplicate provider webhook events.
  • Bad signature, stale timestamp, partial payload, provider timeout.
  • DB write succeeds but PDF fails: safe retry and no duplicate.

VAT/multi-region matrix

  • Domestic/regional/export; B2C/B2B; valid/invalid tax ID; exemption.
  • Tax-rate effective date and legal timezone.
  • Currency code, decimal scale, format and conversion source/timestamp.
  • Line/order discounts, taxable shipping, refunds and credit notes.
  • Boundary values 0.005, 1.005, 19.995; rates 0%, 5%, 15%, 20%.

Batch job runbook

  1. Define expected input/output count, duration SLO and idempotent rerun policy.
  2. Record run ID, cursor/watermark, start/end, status, retries and error reason.
  3. Alert on failure, duration anomaly, count mismatch and backlog growth.
  4. Reconcile source orders to invoices after every run.
  5. Assign triage owner, customer impact assessment, remediation and retrospective.

Interview drills

“Prove it” question bank

How would you test an invoicing feature end-to-end?

Start with order-state transitions and invariants. Test happy path, tax/discount/rounding boundaries, retries, authorization, PDF readability and records. Use Playwright for behaviour, API/schema checks for contract, and independent SQL reconciliation for persistence. Add job monitoring and a recovery story.

A Playwright test is flaky in CI but passes locally. What do you do?

Inspect trace, network, console, data and parallelism. Check shared accounts, worker timing, clock/timezone and selector stability. Wait for the business event, isolate data and make cleanup deterministic. Do not start by increasing timeout or retry count.

How do you validate a financial total?

Agree calculation/rounding rule with Finance/Product. Derive expected values independently from line data using exact decimals. Compare UI/API/database/PDF; cover discount, shipping, tax, currency and refund cases. Retain an audit trail and alert on exceptions.

Why impact.com and an Invoicing Squad?

impact.com publicly describes a partnership platform with Contract & Pay capabilities that connect outcomes to partner compensation. That makes auditable financial behaviour meaningful. I want to apply hands-on checkout/invoice work and a verify-first approach where data integrity directly affects customers and the business.

How do you use AI safely in QA?

I use it for first drafts and coverage ideas, then verify against contract, schema, policy, expected calculations and a real run. I independently derive financial expectations and treat generated output as untrusted until tested.

Playwright configuration - line by line

Understand the test runner settings

This is the same configuration with comments explaining why each setting exists and how to discuss it in an interview.

// playwright.config.ts
// Import Playwright's configuration helper and predefined device profiles.
import { defineConfig, devices } from '@playwright/test';

// Export the single configuration object Playwright reads when it runs tests.
export default defineConfig({
  // Tell Playwright where test files live, relative to this config file.
  testDir: './tests',

  // Fail one test after 30 seconds. This is a safety limit, not a wait strategy.
  timeout: 30_000,

  // Give web-first assertions such as expect(locator).toBeVisible() five seconds to retry.
  expect: { timeout: 5_000 },

  // Run independent tests concurrently to reduce total execution time.
  // Tests must have isolated accounts/data before enabling this.
  fullyParallel: true,

  // In CI, fail the run if test.only() was accidentally committed.
  // Locally this remains false so focused debugging is still possible.
  forbidOnly: !!process.env.CI,

  // Retry failed tests twice in CI to collect diagnostic evidence for intermittent failures.
  // Do not use retries as the only response to flaky tests; fix the cause.
  retries: process.env.CI ? 2 : 0,

  // Generate an HTML report without automatically opening a browser in CI.
  // Also show a compact list reporter in terminal output.
  reporter: [['html', { open: 'never' }], ['list']],

  // Apply these defaults to every test unless a project or test overrides them.
  use: {
    // Resolve relative page.goto() paths, e.g. page.goto('/account/login/').
    baseURL: 'http://127.0.0.1:8000',

    // Record a detailed trace only on the first retry, balancing evidence with storage cost.
    trace: 'on-first-retry',

    // Save screenshots when a test fails, giving a quick visual failure clue.
    screenshot: 'only-on-failure',

    // Retain video only for failed tests, useful for timing or visual regressions.
    video: 'retain-on-failure',
  },

  // Define browser/device combinations; every test runs once per project by default.
  projects: [
    // Use Playwright's Desktop Chrome profile for desktop coverage.
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },

    // Use the Pixel 5 profile to exercise the mobile layout and touch viewport.
    { name: 'mobile-chrome', use: { ...devices['Pixel 5'] } },
  ],
});
Interview-ready explanation: “I set conservative timeouts, web-first assertion retries and failure diagnostics. Parallelism is valuable only when tests are isolated. CI retries provide trace evidence, but I investigate the root cause rather than masking flakiness.”
  • I can explain the difference between test timeout and expect timeout.
  • I can name the test-data risks of fully parallel execution.
  • I know when to use trace, screenshot and video artifacts.
