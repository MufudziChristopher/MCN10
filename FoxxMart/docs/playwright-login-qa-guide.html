What you will test

The login URL is http://127.0.0.1:8000/account/login/. The practical backend scope is the 3rd Axis store’s versioned API, cart behaviour, test checkout, invoice snapshot, PDF endpoints, order lifecycle, returns, stock, and totals. Login remains the safe entry point for authenticated API work.

Testing boundary: use a dedicated local/test account. Never put a real password, OAuth secret, or production customer data in a test file, trace, screenshot, or report.

2. Write your first login-page test

Create tests/login.spec.ts. Start with visible user outcomes—not implementation details such as CSS class names.

import { test, expect } from '@playwright/test';

test.describe('Foxx Mart login', () => {
  test('shows a focused, cart-free login experience', async ({ page }) => {
    await page.goto('/account/login/');

    await expect(page.getByRole('heading', { name: 'Sign in to Foxx Mart' })).toBeVisible();
    await expect(page.getByLabel('Email address')).toBeVisible();
    await expect(page.getByLabel('Password')).toBeVisible();
    await expect(page.getByRole('link', { name: 'Forgot password?' })).toBeVisible();
    await expect(page.getByRole('button', { name: 'Sign in' })).toBeVisible();

    await expect(page.getByText('Quick Cart')).toHaveCount(0);
    await expect(page.getByTitle('Cart')).toHaveCount(0);
  });
});

Run it with npx playwright test tests/login.spec.ts. The page object is a browser tab supplied by Playwright’s built-in fixture; expect waits automatically for the assertion’s condition.

4. Understand fixtures and test suites

A fixture is reusable setup and cleanup supplied to a test. Playwright gives you page, browser, and context. You can extend them with an authenticated page or an API client.

// tests/fixtures.ts
import { test as base, expect } from '@playwright/test';

type Fixtures = { loginPage: import('@playwright/test').Page };

export const test = base.extend<Fixtures>({
  loginPage: async ({ page }, use) => {
    await page.goto('/account/login/');
    await expect(page.getByRole('heading', { name: 'Sign in to Foxx Mart' })).toBeVisible();
    await use(page); // hand the prepared page to the test
    // optional cleanup belongs after use()
  },
});
export { expect };
// tests/login.spec.ts
import { test, expect } from './fixtures';

test.describe('Foxx Mart login', () => {
  test('has a password-recovery route', async ({ loginPage }) => {
    await loginPage.getByRole('link', { name: 'Forgot password?' }).click();
    await expect(loginPage).toHaveURL(/\/reset_password\//);
  });
});

test.describe groups related scenarios for reporting and shared hooks. Use test.beforeEach for cheap, isolated setup; use beforeAll only for safe, read-only or globally managed setup. Tests should be able to run alone, in any order, and in parallel.

5. Explain async and await confidently

Browser actions take time: navigation, clicks, rendering, and network calls are asynchronous. An async test returns a Promise. await pauses that test until the action completes, without blocking other tests or the Node.js event loop.

// Correct: complete each important action before relying on its result.
await page.getByRole('button', { name: 'Sign in' }).click();
await expect(page).toHaveURL(/\/mall\//);

// Risky: the assertion may run before a navigation caused by the click.
page.getByRole('button', { name: 'Sign in' }).click();
await expect(page).toHaveURL(/\/mall\//);

Playwright assertions retry automatically until their timeout. This is different from adding a blind waitForTimeout(2000), which only makes a slow test slower and a very slow test still flaky.

6. Test responsive menu collapse

The menu is expanded at page load and should collapse after a vertical scroll of more than 96px on desktop and mobile. The behavior is an ideal interview-quality UI test because it tests a user-visible state transition.

test('collapses the login menu after scrolling', async ({ page }) => {
  await page.goto('/account/login/');
  const menu = page.locator('[data-account-menu]');

  await expect(menu).not.toHaveClass(/is-collapsed/);
  await page.evaluate(() => window.scrollTo(0, 120));
  await expect(menu).toHaveClass(/is-collapsed/);
});

Run this in both configured projects: npx playwright test --project=chromium and npx playwright test --project=mobile-chrome. If the login page is too short to scroll in a chosen viewport, test this rule on a longer account/store page, or add purposeful test-only content—not arbitrary waits.

7. API testing: turn browser risk into contract checks

Use the UI for the few journeys a shopper sees; use the API for fast, precise coverage of rules and edge cases. 3rd Axis exposes GET /3rdAxis/api/v1/products/, GET /3rdAxis/api/v1/products/:id/, GET /3rdAxis/api/v1/cart/, and POST /3rdAxis/api/v1/cart/items/. The cart endpoints require an authenticated user with Axis access.

RiskBest levelUseful assertion
Product data shape changesAPI contractEvery product has ID, name, two-decimal price, numeric stock, and currency semantics.
Out-of-stock product is oversoldAPI + SQLPOST returns 409; stock and cart rows do not change.
Cart total is wrongAPI + SQLAPI line totals, cart total, and database calculation agree.

First public API contract test

import { test, expect } from '@playwright/test';

test('products contract exposes safe, typed fields', async ({ request }) => {
  const response = await request.get('/3rdAxis/api/v1/products/');
  await expect(response).toBeOK();

  const body = await response.json();
  expect(Array.isArray(body.products)).toBeTruthy();
  expect(body.products.length).toBeGreaterThan(0);

  for (const product of body.products) {
    expect(product).toMatchObject({
      id: expect.any(Number),
      name: expect.any(String),
      stock: expect.any(Number),
    });
    expect(product.price).toMatch(/^\d+\.\d{2}$/);
    expect(product.stock).toBeGreaterThanOrEqual(0);
    expect(product).not.toHaveProperty('cost_price'); // a useful data-leak check
  }
});

Interview language: this is not merely a status-code test. It verifies the contract that a UI or partner integration depends on, checks data quality, and guards against accidental exposure of internal fields.

Authenticated API fixture without secrets in test code

// tests/auth.setup.ts — run once to create a reusable, local storage state
import { test as setup, expect } from '@playwright/test';

setup('authenticate QA shopper', async ({ page }) => {
  await page.goto('/account/login/');
  await page.getByLabel('Email address').fill(process.env.E2E_EMAIL!);
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page).toHaveURL(/\/mall\//);
  await page.context().storageState({ path: 'playwright/.auth/shopper.json' });
});

// In playwright.config.ts, make API/UI projects depend on this setup project.
// Add playwright/.auth/ and .env.test to .gitignore.
// tests/cart-api.spec.ts
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/shopper.json' });

test('rejects an attempt to add an out-of-stock item', async ({ page }) => {
  // BrowserContext.request shares the authenticated browser context's cookies.
  const api = page.context().request;
  const products = await (await api.get('/3rdAxis/api/v1/products/')).json();
  const outOfStock = products.products.find((product: { stock: number }) => product.stock === 0);
  test.skip(!outOfStock, 'Seed an out-of-stock product before running this test.');

  const before = await api.get('/3rdAxis/api/v1/cart/');
  const beforeBody = await before.json();
  const response = await api.post('/3rdAxis/api/v1/cart/items/', {
    data: { productId: outOfStock.id, action: 'add' },
  });

  expect(response.status()).toBe(409);
  expect(await response.json()).toEqual({ error: 'This item is out of stock.' });
  expect(await (await api.get('/3rdAxis/api/v1/cart/')).json()).toEqual(beforeBody);
});
Important: do not use a shared cart when tests run in parallel. Give every worker a distinct test user, or clean/reseed the data before every test. A test that changes stock must restore it in teardown or, better, run in a disposable database.

8. SQL testing: independently verify the ledger

SQL is a powerful QA diagnostic and reconciliation tool. It should run only against a local or dedicated test PostgreSQL database, using least-privilege read access where possible. It is not a substitute for testing business behaviour through supported interfaces.

Connect safely

# Your local/test connection string only; never paste a production password into a workbook.
psql "$DATABASE_URL"

# Inspect tables rather than guessing their names.
\dt axis_*
\dt account_*
\d axis_order
\d account_invoice

Reconcile an Axis order subtotal

-- Replace :order_id with the order you created in the test environment.
SELECT
  o.id AS order_id,
  o.status,
  COALESCE(SUM(oi.quantity * p.price), 0)::numeric(12,2) AS calculated_subtotal,
  COUNT(oi.id) AS distinct_lines,
  COALESCE(SUM(oi.quantity), 0) AS item_count
FROM axis_order AS o
LEFT JOIN axis_orderitem AS oi ON oi.order_id = o.id
LEFT JOIN axis_product AS p ON p.id = oi.product_id
WHERE o.id = :order_id
GROUP BY o.id, o.status;

Compare calculated_subtotal with the API’s total while the cart is pending. The Axis pricing rule is: grand total = subtotal + R99.00 delivery + 15% VAT on (subtotal + delivery), rounded to two decimal places. Always clarify the tax base with product before treating this as a defect.

Reconcile invoice snapshots

SELECT
  i.id, i.store_slug, i.order_reference, i.status,
  i.subtotal, i.delivery_fee, i.vat_amount, i.total,
  (i.subtotal + i.delivery_fee + i.vat_amount)::numeric(12,2) AS recomputed_total,
  i.issued_at
FROM account_invoice AS i
WHERE i.store_slug = 'axis'
  AND i.order_reference = :order_id;

-- This should return zero rows. If it returns data, the idempotency invariant is broken.
SELECT user_id, store_slug, order_reference, COUNT(*)
FROM account_invoice
GROUP BY user_id, store_slug, order_reference
HAVING COUNT(*) > 1;

Find suspicious state

-- No product should have negative stock.
SELECT id, name, stock FROM axis_product WHERE stock < 0;

-- Confirm line totals are never based on a null product.
SELECT oi.id, oi.order_id
FROM axis_orderitem AS oi
WHERE oi.product_id IS NULL;

-- Confirm a completed/payment-confirmed Axis order has exactly one invoice.
SELECT o.id, o.status, COUNT(i.id) AS invoices
FROM axis_order AS o
LEFT JOIN account_invoice AS i
  ON i.store_slug = 'axis' AND i.order_reference = o.id::text
WHERE o.status = 'Payment confirmed'
GROUP BY o.id, o.status
HAVING COUNT(i.id) <> 1;
How to describe SQL testing in an interview
“I use SQL to validate persistence and cross-check financial invariants after exercising the public interface. I make the query deterministic, scope it to seeded data, and clean up afterward. I do not couple every UI test to the database; I reserve it for high-risk flows such as money, stock, state transitions, and data migration.”

9. Invoice and total lab

Foxx Mart creates an invoice snapshot after a confirmed checkout. It records the store, order reference, transaction ID, status, subtotal, VAT, delivery fee, total, and JSON item snapshot. The profile page exposes view/download invoice endpoints using a public UUID owned by the logged-in customer.

  1. Create a test order with two different products and a quantity greater than one.
  2. Record the cart API response before checkout: line items, count, and subtotal.
  3. Complete the local test checkout with a valid shipping address and choose whether to save it.
  4. Assert redirect to /account/?store=axis, then locate the new invoice link.
  5. Open the view and download URLs. Assert Content-Type: application/pdf and a useful filename.
  6. Use the SQL reconciliation query to verify exactly one invoice and the calculated total.
test('confirmed checkout produces one owned PDF invoice', async ({ page }) => {
  // Precondition: a dedicated QA user has a pending cart with seeded items.
  await page.goto('/3rdAxis/checkout/');
  await page.getByLabel('Country').selectOption({ label: 'South Africa' });
  await page.getByLabel('Street address and number').fill('1 Test Lane');
  await page.getByLabel('Suburb / area').fill('QA Park');
  await page.getByLabel('City / town').fill('Cape Town');
  await page.getByLabel('Province').selectOption({ label: 'Western Cape' });
  await page.getByLabel('Postal code').fill('8001');
  await page.getByRole('button', { name: /confirm test order/i }).click();
  await expect(page).toHaveURL(/\/account\/\?store=axis/);

  const invoice = page.getByRole('link', { name: 'View PDF' }).first();
  await expect(invoice).toBeVisible();
  const pdf = await page.context().request.get(await invoice.getAttribute('href')!);
  expect(pdf.headers()['content-type']).toContain('application/pdf');
  expect(pdf.headers()['content-disposition']).toContain('foxx-mart-invoice-');
});

10. Admin and order-state lab

The Axis order lifecycle includes Pending, Payment confirmed, Picking items, Packed, Awaiting courier, Collected by courier, In transit, Out for delivery, Delivered, Delivery exception, and Cancelled. Test the operations interface or Django Admin with a designated test administrator—not your everyday shopper session.

Pending → Payment confirmedPayment event should create one invoice and stable transaction ID.UI message, order row, invoice, SQL reconciliation.

test('operations user can mark a confirmed order as picking', async ({ page }) => {
  await page.goto('/account/admin-dashboard/');

For a QA interview, call out the distinction: an administrator changing a status is not proof that downstream actions happened. Identify the expected events—notification, stock reservation/release, invoice immutability, courier integration—and test each at the right layer.

11. QA Engineer interview rehearsal

Tell this testing story

“I start with risk and the money flow. In Foxx Mart I would cover login as the authenticated entry point, then test API contracts for products and carts, out-of-stock protection, pricing calculations, checkout idempotency, invoice generation, ownership controls, and order/return state changes. I use Playwright fixtures and isolated QA data, assert response plus persisted state for high-risk flows, and use SQL to reconcile totals and investigate defects. I use retries only to surface instability, then inspect traces and remove the cause.”

Questions to practise

  • How do you choose whether a risk belongs in a unit, API, UI, or database test?
  • How would you test a checkout flow without touching a real payment provider?
  • What makes an invoice idempotent, and how would you prove it?
  • How do you verify a total without duplicating all the application’s implementation in a test?
  • How would you test API authentication, authorization, validation, and rate/error handling?
  • How do Playwright API contexts, browser storage state, fixtures, and async/await work together?
  • How would you investigate a test that fails only in CI or only under parallel execution?

60-minute practice plan

  1. Run the product contract test and deliberately break one expectation in a branch; read the report.
  2. Build one negative cart API test and explain the status code, payload, and state invariant.
  3. Create a two-line order, calculate expected subtotal/VAT/total on paper, then reconcile it with SQL.
  4. Run the invoice workflow. Refresh/retry the last action and prove there is only one invoice.
  5. Open trace/report artifacts and give the testing story above as a two-minute answer.

Completion checklist

  • I can initialise Playwright and run tests headlessly or in UI mode.
  • I can explain test, expect, page, request, async, and await.
  • I can write API contract, validation, and authorization tests with isolated data.
  • I can reconcile an order, cart, inventory value, and invoice total using safe SQL.
  • I can explain idempotency, eventual consistency, state transitions, and test data ownership.
  • I can use traces, screenshots, SQL evidence, and retries to diagnose—not hide—flakiness.
  • I can present a risk-based testing strategy for a financial/order workflow in plain language.
